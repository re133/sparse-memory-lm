A tiny language model with a huge lookup table

Short answer: yes, the table is worth it. And the more the model trains, the more it's worth.

The two-minute version · by Leon Fechner · last updated 23 October 2026

I took a small language model (21M parameters) and gave it a table with up to 16.8 million learned vectors. For every token (roughly a word) it only looks up a few hundred of them, so it barely computes more than before. Then I trained normal models of different sizes on exactly the same data, to see how big a normal model has to be to keep up.

Newest: three more experiments at home

23 October 2026, afternoon

Training the 16.8M table is now 1.4 times as fast, in 30 instead of 52 GiB of RAM. The 5% most-read rows stay on the GPU, and each step's gradients are summed there instead of in a table-sized buffer in RAM. Over 20M tokens the curve was 1.5% worse at first and 0.3% at the end. An exact rerun of the old way was itself 0.75% off, so I can't tell yet whether that's more than noise.

Letting the model grow didn't pay off. I started the 4M-table model with half of its plain layers asleep and woke them up after 40M tokens, so that they start out changing nothing. The small model was only 18% faster, probably because the output layer, the table reads and the remaining layers still cost the same. At the same training time the grown model ended up where the normal one did (0.7% behind).

Teaching the model to be written into works, but so far it costs too much. In 150 short episodes I wrote made-up people into the table and trained the rest of the model to answer questions about them. Afterwards, facts written in wordings it had never seen came back right 74% of the time instead of 50%. But the training itself made the model forget part of what it knew (people it had learned: 80% right instead of almost 100%), and normal text got 4.4% worse. With five times gentler training the text stayed the same, but most of the gain was gone (55% instead of 50%) and the model still forgot part of what it knew. So the gain and the forgetting seem to come together; next I'd change something narrower than the whole model.

Training at home with less memory

23 October 2026

Half the memory a big table needs during training isn't the table, it's the optimizer: Adam keeps two extra numbers for every value in it. I tried keeping just one number per table row instead, and repeated two earlier runs with it, written down beforehand as always.

The 16.8M table trained 1.9% better in half the RAM (52 instead of about 100 GiB, table in RAM, 100M tokens). It wasn't faster, though: copying rows to the GPU is still what takes the time.

The 4M table now trains entirely on my 16 GB gaming card. Before, it needed 28.5 GiB on an H200. Now it uses 14.7 GiB, runs at 40,600 tokens per second (78% of the H200's speed) and after 100M tokens was 1.3% better than the H200 run on Wikipedia, though 1.4% worse on WikiText-103. In both runs the lead shrank as training went on, so I don't know yet if it lasts.

Writing facts straight into the table

22 October 2026

Next idea: train the small model once, and later just write new knowledge into the table instead of training again. I took the finished model and 150 made-up people it had never seen. For each one it read a short profile 16 times in a row, and each time I only nudged the table rows it had read. No optimizer, the rest of the model frozen.

The new facts stuck: 98% right afterwards (before: 2%), in under half a second per person. Normal text didn't get worse at all.

The catch at first: people it had learned in training dropped from about 100% to 52–79% right, because most of the rows a question like "… was born in" reads are shared by every person. The fix turned out to be a gentler nudge: with a tenth of the step size the new facts are still 99% right, and the known people stay 96–99% right. They are a bit less certain than before, so by my own bar it's close, but not done yet.

Six times the training

18 October 2026

The obvious objection: with more training, the normal models catch up and the table becomes pointless. So I trained everything again on 3 billion instead of 500 million tokens. I wrote down the rule for "grows", "holds" and "shrinks" before the runs, and my own guess was "holds" or "shrinks".

It grew, for all three table sizes.

What else works

  • The table doesn't have to sit on the GPU. From normal RAM or even an NVMe SSD the model still writes 114 to 154 tokens per second on my PC.
  • It trains on a gaming card. The 16.8M table trained on my 16 GB Radeon RX 9070, with the table in RAM, and came out as good as on a big H200. It just took 7.7 times as long. The 4M table fits on the card itself.
  • It helps to remember facts. Facts about made-up people, seen only a few times in training, stuck clearly better with the table than in a normal model with twice the compute.
  • Same code on AMD and NVIDIA. The kernels run unchanged on a Radeon RX 9070, an AMD Instinct MI350X and NVIDIA H100/H200.

The catch

  • Training takes longer. On an H200 a normal model gets to the same quality in 19 to 27% less time. Looking things up in the table isn't free.
  • Not faster in use yet. On an H200 it doesn't write text faster than a normal model of the same quality. It computes much less, but at this small size computing isn't the bottleneck.
  • It mostly helps on text like its training data. On a differently formatted text set (WikiText-103) the advantage is much smaller.
  • Still small. The biggest normal model I compared against has 400M parameters, and every model was trained once.
  • Bolting a table onto a finished model didn't work (tried on Qwen3.5-0.8B).

What's next

The real question is whether this holds at a size people actually use: a model around 1 billion parameters with a table of tens of millions of rows. That needs bigger GPUs than I can rent.
